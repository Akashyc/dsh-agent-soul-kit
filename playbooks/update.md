# playbook · 更新

- 对上游：`AGENT-INSTALL.md`（同 install.md §四，锚点未变时不再逐节复核）
- 前置：上游已同步（有更新就拉到最新，再动手）；`probe/upstream.mjs` + `probe/local.mjs` + `probe/diff.mjs` + `probe/files.mjs` 已跑通
- 产物：更新后的 apply / meta / report，旧的那个不覆盖，按时间戳并存

## 一、目标

把上游这一版的变化带到本机，**同时不让「用户自己改过的东西」被静默盖掉**。

三件事必须同时成立：

1. 上游变得地方变了，没变的地方不动；
2. 本机被用户改过的地方，覆盖前先说出来；
3. 补丁层清空重来——**旧补丁不打在没验证过的新版本上**。

第 3 条不是洁癖：补丁的上下文是旧文件的，上游一改，`fix.patch` 十有八九打不上，而 `patch` 打不上时默认行为是**留一堆 `.rej` 文件继续往下走**。宁可重打，不要残骸。

## 二、先判断该不该更新

`meta.json` 存了四项指纹。逐项比对，**别凭「上游好像更新了」的感觉动手**：

| 指纹 | 比什么 | 由谁提供 |
|---|---|---|
| `upstream` | 提交号 + 零件清单哈希 | `upstream.sha`、`diff.json` |
| `local` | 已装文件的逐文件哈希 | `files.json` 的 `shaB` |
| `kit` | kit 自己的版本号 | `package.json` |
| `answers` | 选项内容哈希 | `answers.json` |

### 四种情况的处置

| upstream | local | 结论 | 怎么做 |
|---|---|---|---|
| 没变 | 没变 | 不需要更新 | 一句话说明，不动手 |
| 变了 | 没变 | 正常更新 | 按 §三 走 |
| 没变 | 变了 | **本机被人改过** | 报告差异文件清单，问用户：保留改动，还是覆盖 |
| 变了 | 变了 | 两边都动过 | 先给 `files.json` 的差异清单，逐条问；**不整体覆盖** |

`local` 变了的典型来源：用户自己调了插件、上一轮补丁写进了文件、别的工具改过。这三种的处理方式不一样，但**共同点是：不能当成「上游变了」一起盖掉**。

kit 版本变了但上游没变 → 不必重装，只要 `apply/` 里引用的接口还成立。判断方法是读一眼 apply 用的 probe 输出字段名有没有变；不确定就重跑一次干跑对比。

## 三、差异 → 动作

`diff.mjs` 把结构差异分成四类，`files.mjs` 管内容。**先处理结构，再处理内容**——结构变了，内容比较的基线也就变了。

| 差异 | 来自 | 动作 | 要问用户吗 |
|---|---|---|---|
| `added`（上游新增零件） | diff | 装不装？ | **要**，除非上次 `declined` 里明确拒过同名包 |
| `removed`（上游删了零件） | diff | 本机对应目录要不要清 | **要**——清目录会连带删掉用户在里面放的东西 |
| `renamed`（dir 改名） | diff | 建新目录 + 清旧目录 + **改所有引用** | 不用问，但要在报告里列出改了哪几处 |
| `changed`（manifest 字段变） | diff | 覆盖 `package.json` | 版本变化要报，其余静默 |
| 内容变（文件哈希） | files | 覆盖该文件 | 不用问，除非 §二 判定 local 也被改过 |
| 锚点变 | diff.headings | 按 install.md §四 的「锚点对不上时」处理 | **要**，判不出类别就停 |

### 改名是最容易漏的

`renamed` 的处置**不能只做目录操作**。名字变了，引用它的每一处都得跟着改：

1. 跑 `probe/references.mjs --name <新旧两个名字>`；
2. 把命中的文件清单报给用户看；
3. 逐个改，改完再跑一次同样的命令，确认旧名字只剩 0 处。

**以 probe 输出为准，不要凭记忆列清单。** 今天列 5 处，明天上游在第 6 个文件里也引用了这个名字，清单就过期了——而清单看起来永远是「完整的」。

## 四、全量覆盖，补丁清空

更新时**不读补丁，也不考虑补丁打过没打过**。顺序固定：

1. 清掉本机已应用的补丁（如果记了的话），恢复上游原样；
2. 按 §三 覆盖文件；
3. 更新 `meta.json`；
4. 装完后再进诊断阶段，按 [修复补丁](../docs/架构-修复补丁.md) 的规则重新应用或退役。

第 1 步做不到（不知道打过哪些补丁）就**说明白**，别假装清干净了。这种情况下降级为：覆盖后立刻跑一次诊断，看有没有 `stale`。

## 五、验收

同 [install.md §三](install.md)：干跑 → 用户确认 → 真跑 → 三条判据。

更新的额外两条：

| # | 检查 | 失败意味着 |
|---|---|---|
| 4 | 旧目录（`removed` / `renamed` 的源目录）已不存在 | 残留目录会在下次启动时和新的抢同一个插件名 |
| 5 | `references.mjs` 对旧名字的命中数为 0 | 有引用还指着旧名字，插件永远不加载 |

第 4 条不能只看目录删没删——`node_modules` 里可能还有 `.package-lock.json` 之类的残留，按 `local.installedPackages` 重新跑一遍，看清单对不对。

## 六、和安装的分工

| | 安装 | 更新 |
|---|---|---|
| 输入 | 上游一版 + 用户选项 | 上游两版之差 + 本机现状 |
| 会问什么 | 装哪些、装哪个 profile | 新增的装不装、删了的清不清、两边都改过的怎么办 |
| 不做什么 | 不碰已有安装 | 不重问已经答过的选项 |
| 共同点 | 全量写、干跑先行、补丁不参与 | 同左 |

已经答过的选项从 `answers.json` 读，**不重问**。要改选项走单独的入口，不在更新流程里顺手改。
