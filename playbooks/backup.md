# playbook · 备份与还原

- 工具：`kit/backup.mjs`（`plan` / `pack` / `verify` / `restore`）
- 前置：`probe/local.mjs` 能跑通，知道 DSH 目录和 profile 名
- 产物：一个 `.tgz` + 里面的 `.manifest.json`

## 一、目标

保护**重装不会重建的东西**，不保护能重装出来的东西。

这条判据决定了清单长什么样：

| 进包 | 为什么 |
|---|---|
| `dsh-soul/` | 记忆、书房、账本。重装不会重建它 |
| `profiles/<p>/cordis.patch.yml` | 装配清单，重装会被覆盖成作者默认 |
| `profiles/<p>/package.json` | bundles 与依赖声明 |
| `profiles/<p>/skills/` | preset 自带的技能目录 |
| `data/<p>/` | answers / meta / apply / report：你的选择与执行记录 |

| 不进包 | 为什么 |
|---|---|
| `profiles/*/node_modules` | 安装结果，重装能得到，体积最大 |
| `logs/` | 运行期日志属于当时的机器，换机器即失效 |
| `data/_kit/patches/` | 补丁的 diff 上下文在新机器上大概率对不上；还原后重新诊断更可信 |

最后一条是已定决策，不是遗漏。代价是换机器后要重新研究修法——接受这个代价，因为「症状还在不在」本来就该在新机器上重新看。

## 二、必须先问

**备份会写出一个新文件，Agent 不许自行执行 `pack`。** 用户明确说要备份，才走这一节。

顺序固定，中间可以停：

1. `node kit/backup.mjs plan --dsh-home <目录>` —— 清点：哪些进、哪些不进、多少文件、多大；
2. 把清单和 `warnings` 给用户看（缺 `dsh-soul` 必须说，那意味着这份备份没保护到最要紧的东西）；
3. 用户点头，才跑 `pack --out <文件> --yes`；
4. `verify --from <文件>` 确认包能读、manifest 在。

## 三、还原

还原比备份危险：它往一个目录里写东西，而且会**改写文本里的绝对路径**。

1. `restore --from <包> --to <目标目录>`（不带 `--yes`）—— 解包、算好要写哪些文件、要改哪些路径，**目标目录一个字节都不动**；
2. 把 `counts`（新增 / 覆盖 / 跳过）和 `rewrites`（哪个文件改了几处）给用户看；
3. 用户确认后才 `--yes`。

### 路径改写只碰文本

白名单：`.yml .yaml .json .md .mjs .js .txt`。其它一律不改——二进制文件里恰好出现同样的字节序列是完全可能的，改了就坏。

改写发生在**解包后的暂存目录**里，改完才复制进目标目录。所以中途失败不会留下半改不改的目标。

## 四、验收

| # | 检查 | 失败意味着 |
|---|---|---|
| 1 | `verify` 报 `hasManifest: true` | 不知道这包从哪台机器、哪个 profile 打的 |
| 2 | 包里的文件数与 `plan` 的 `total.files` 对得上 | 打包中途漏了东西 |
| 3 | 还原后配置文件里**没有**旧机器路径 | 换机器后插件会去一个不存在的目录找东西 |
| 4 | 还原后目标目录里**没有** `.manifest.json` | manifest 是元数据，落进用户目录就是脏文件 |
| 5 | `dsh-soul/` 还原完整 | 记忆和书房是这份备份唯一不可替代的部分 |

## 五、还原之后必须做的

1. **补丁不会跟着还原。** 跑一次诊断，看哪些症状还在，按 [修复补丁](../docs/架构-修复补丁.md) 重新应用或退役。
2. **`apply/` 里的脚本可能带着旧机器的路径。** 它进包是为了留记录，不是拿来直接跑的——真要用，先按 [apply 契约](../docs/架构-apply契约.md) 重新校验一遍。
3. **重启 DSH。** 这不归 kit 管，但漏了它前面全白做。

## 六、不做

- 不做增量备份。全量 tar 已经够快，增量要维护一套状态，那是另一个产品。
- 不做加密。包里有灵魂数据，加密加不好不如不加——需要加密的场景，用户自己套一层。
- 不做自动定时备份。备份是显式动作，见 §二。
