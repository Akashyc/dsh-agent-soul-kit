# playbook · 诊断

- 工具：`probe/logs.mjs`（取证）+ `kit/patch.mjs plan`（补丁状态）+ `kit/diagnose.mjs`（渲染）
- 前置：一次安装或更新刚做完，或用户说「哪里不对」
- 产物：Markdown（给人看）+ `diagnose.json`（给补丁引擎）

## 一、目标

回答一个问题：**这台机器上，现在有什么是真的坏了。**

不是「看起来很可疑」，不是「理论上可能有问题」——是能指到证据的那种。

所以先取证，再判断，最后才渲染。顺序反了就会变成「照着模板找问题」。

## 二、先取证

    node probe/logs.mjs > <run>/logs.json
    node probe/upstream.mjs --source <作者仓库> > <run>/upstream.json
    node probe/local.mjs > <run>/local.json
    node kit/patch.mjs plan --profile-dir <profile 目录> > <run>/patch-plan.json
    node kit/diagnose.mjs --run <run>

四份输入缺一份，诊断就有一块是「未判定」——**这是对的，不要用推测补上。**

### 范围由上游清单决定，不是常量表

`probe/logs.mjs` 会收下所有 error。`kit/diagnose.mjs` 用 `upstream.json` 的零件清单过滤：

- 包名在清单里 → 算本架构的零件，进「正在发生」
- 不在清单里 → 概览里单独报一条「另有 N 条不在上游零件清单里，未计入」

实测（2026-11-06）：本机 15 条 error 全部来自 `@deepseek-ai/dsh-agent-loop` 和 `@deepseek-ai/dsh-tools`，一条都不属于上游零件。混进去就会得出「零件全在崩」的假结论。

**这不写死任何包名。** 上游新增零件，清单自动包含；宿主组件永远不在清单里，也就不需要一份「宿主要排除」的维护表。

## 三、三段式，只有三段

渲染结果只允许这三种段落，顺序固定：

| 段 | 内容 | 什么时候出现 |
|---|---|---|
| 一、正在发生 | 有日志证据、且属于本架构零件的错误 | 有才出现 |
| 二、作者已修 → 改用作者的 | 上游变了且症状消失 | 有才出现 |
| 三、新发现 | stale 补丁、认不出归属的错误、上游结构变化 | 有才出现 |

**空段整段消失，序号按实际出现的段落从「一」连续编号。** 只有「新发现」时它就是「一」，不写「三、新发现」留两个空号。

概览行必须写清范围：读了几份日志、扫了几个零件、有多少条被排除在外。**不许写「全部正常」。**

## 四、三条不许踩的线

1. **全零只代表读取范围内没有匹配项。** 不能扩写成「没有问题」。
2. **没有可读日志必须写「未判定」**，不能拿 0 代替「没检查」。
3. **没发现问题时不主动追问要不要写盘**，也不把没分析过的 warn 判成「无关」「偶发」。

## 五、报文只说一行

多行栈会把 Markdown 标题冲垮。渲染时只取报文第一行、限 140 字，全文留在 `logs.json` 里。

要读完整栈，去看 `logs.json` 的对应条目——**不要在渲染层做摘要**，那是把证据二次加工。

## 六、验收

| # | 检查 |
|---|---|
| 1 | 概览的三个计数与段落里的条目数对得上 |
| 2 | 没有空段，序号连续 |
| 3 | 每条都有「证据」，没有证据的进「新发现」并标「待核对」 |
| 4 | 日志不可读时 verdict 是 `undetermined`，正文里有「未判定」 |
| 5 | 范围外的错误没有混进「正在发生」 |

## 七、想反馈作者时

那是另一件事，用 `kit/report.mjs`，见 [诊断与交付](../docs/架构-诊断与交付.md) §三。日常诊断不要写成长报告。
