# dsh-agent-soul-kit

**版本 1.0.0** · MIT · macOS / Windows / Linux

给 Agent 用的作业指导书与取证工具包。它本身不替你装东西——它把「作者上游现在长什么样、你这台机器现在是什么状态」变成结构化事实，让 Agent 按你的选择现场生成这一次要执行的脚本。

## 为什么不是一键安装

上游会变：新增零件、改包名、调安装流程。任何写死这些决定的安装器，迟早和上游对不上，而且对不上的时候你只会看到一句报错。

所以这里的分工是：

| 谁 | 干什么 |
|---|---|
| 指导书（playbooks） | 说清该看什么、怎么判成功、失败长什么样 |
| 取证脚本（probe） | 只读：把上游结构、本机状态、差异、日志变成 JSON |
| Agent | 读上面两样，生成这一次的安装 / 更新脚本，干跑给你看，你点头再真跑 |
| 你 | 选装什么、叫什么名字、要不要打补丁 |

生成的脚本留在本机，不进仓库。

## 先同步上游

五件事都从同一个动作开始：把作者仓库同步到 `upstream/dsh-agent-soul`。

| 本机状态 | 做什么 |
|---|---|
| 还没有 | 克隆一次 |
| 有，上游没动 | 直接往下走 |
| 有，上游有新提交 | 快进到最新，再往下走 |
| 本地被改过 / 分叉了 | 停下报出来——覆盖、stash、reset 一概不做 |

理由很简单：所有判断——装哪些零件、哪些文件变了、哪个补丁该退役——都以「作者这一版」为准。读一份旧副本，等于拿过期地图找路，而且看不出它过期。

`upstream/` 在 `.gitignore` 里，不进仓库。它只是本机读作者代码用的副本，删了重跑一次就回来。

## 交给 Agent 开始

把本目录放到一个固定位置，让能读写本机文件的 Agent 以它为工作区。每件事的开场都是同一句型：

> 先同步上游，再读 AGENTS.md，然后按 playbooks/<哪一份> 做 <哪件事>，每一步先跟我确认。

五件事：安装、更新、备份、还原、诊断。补丁不单独触发，最后单列。

### 安装

> 读 AGENTS.md，然后按 playbooks/install.md 帮我把 dsh-agent-soul 装到这台电脑上。每一步先跟我确认。

它先问你三件事：装哪个 profile、装哪些零件、用哪些 preset。然后生成 `data/<profile>/<instance>/apply/`，跑一遍干跑，把「要覆盖哪些文件、要装哪些包、跳过什么、风险在哪、回滚点在哪」列给你。

**你点头之后才真跑。** 跑完它会说「已安装，等待重启后验收」——重启这一步不归它管，也不用它假装管了。

### 更新

> 读 AGENTS.md，然后按 playbooks/update.md 看看上游变了什么，能更就更。

它先比四项指纹：上游提交、本机已装文件、kit 版本、你上次的选择。然后告诉你哪些零件是新增、哪些改了目录名、哪些文件内容变了。

**被你改过的地方会单独列出来问。** 本机文件和上游对不上有两种原因——作者改了，或者你自己动过。后者不会静默覆盖。改名会顺带查一遍引用，确认旧名字一处不剩。

### 备份

> 读 AGENTS.md，然后按 playbooks/backup.md 给我做一份备份，先只清点。

**不会直接打包。** 先出一份清单：哪些进包、哪些不进、多少文件、多大、缺了什么。

- 进包：`dsh-soul/`（记忆、书房、账本）、`cordis.patch.yml`、`package.json`、preset 技能、`data/<profile>/` 里的选择记录
- 不进包：`node_modules`（重装能得到）、`logs/`（属于当时的机器）、补丁库（换了机器 diff 就废）

清点里要是没有 `dsh-soul`，它会明说「这份备份不含灵魂数据」。你说「打」，它才打。

### 还原

> 读 AGENTS.md，然后按 playbooks/backup.md 把 <备份包> 还原到 <目录>，先给计划。

它把包解开、检查、算账：要新增哪些文件、覆盖哪些、配置里有几处旧路径要改写。

**目标目录一个字节都不动**，等你看完清单点头。路径改写只碰 `.yml .yaml .json .md .mjs .js .txt`——二进制里恰好出现同样的字节串很常见，改了就坏。

还原完还有三件事要提醒你：补丁不跟着还原（要重新诊断）、`apply/` 里可能带着旧机器路径（别直接跑）、重启 DSH。

### 诊断

> 读 AGENTS.md，然后按 playbooks/diagnose.md 看看现在有什么是真坏的。

只读，不改任何东西。产出固定三段，空段整段消失，序号连续：

```
**概览**：<上游提交> · kit <版本> · 要修 N · 待退役 M · 新发现 K · 范围：读了什么

一、正在发生
二、作者已修 → 改用作者的
三、新发现
```

两条硬规矩：**全零只代表读取范围内没有匹配项**，不写成「一切正常」；**没有可读日志写「未判定」**，不拿 0 代替「没检查」。

日志里不属于本架构零件的错误（比如 DSH 宿主自己的限流）会在概览里单列「另有 N 条未计入」，不混进结论。

### 补丁

补丁没有独立入口，它挂在诊断后面：

- 诊断发现某个问题已经有验证过的修法 → 问你要不要打；
- 打之前比对目标文件哈希，对不上就报 `stale` 并说清差在哪，**不静默跳过**；
- 安装和更新会把它全量覆盖掉，这是设计不是 bug——每次装完重新诊断、重新决定。

生成一条**新**补丁必须你确认。复用已验证的不用问，因为那个问题已经修过一次了。

## 目录

| 路径 | 是什么 |
|---|---|
| `AGENTS.md` | 给 Agent 的边界与红线 |
| `playbooks/` | 安装、更新、备份还原、诊断的判据与验收 |
| `probe/` | 只读取证脚本 |
| `kit/` | 会写东西的那一层：补丁引擎、备份还原、诊断渲染、导出报告 |
| `docs/` | 架构设计（给维护者看） |
| `data/` | 本机运行数据，不进 Git |
| `upstream/` | 作者仓库的本地副本，不进 Git |

## 三件不做的事

1. **不改上游。** `upstream/` 或 `--source` 指定的目录是只读来源。
2. **不替你做决定。** 装哪些零件、用什么名字，都是问出来的。
3. **不自动提交。** 本工具不 `git commit`、不 `git push`。

## 数据放哪

    data/
    ├── <profile>/<instance>/apply/    # 你的选择、生成的脚本、干跑报告
    └── _kit/                          # 补丁库、运行记录

整个 `data/` 被 `.gitignore` 排除。移动或删除本目录前先想清楚——里面是你这台机器的安装依据。
